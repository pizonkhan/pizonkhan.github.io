# pk-site-analytics

The ingestion and serving Worker behind `pizonkhan.github.io`'s own analytics. It takes page
view, click and visible-time events from the browser, validates them, writes them to a
Cloudflare D1 database, rolls each closed day up into a set of serving tables overnight, and
answers the dashboard's `/stats` request from those tables rather than scanning the raw log.

This directory is a plain sibling package, not an npm workspace member of the site. It has
its own `package.json` and lockfile and is invisible to the site's `tsc`, `eslint` and
`vitest` runs. See the site's `docs/plans/site-analytics-pipeline-and-dashboard.md` for the
full design and the reasoning behind it.

## Layout

```
migrations/     Two migrations: the event landing table, then the seven rollup tables.
src/            fetch and scheduled handlers, validation, normalisation, SQL.
test/           Vitest, run inside a local Workers runtime with a local D1. No account needed.
```

## Running it locally

```bash
npm install
npm run dev        # wrangler dev, serves on localhost:8787 against a local D1
npm test            # the full suite, local workerd + local D1, no network required
npm run typecheck
```

`npx wrangler dev --test-scheduled` plus
`curl "http://localhost:8787/__scheduled?cron=17+1+*+*+*"` triggers the nightly rollup by
hand.

## Endpoints

- `POST /collect`: accepts up to 20 events per body, 8,192 bytes max, as a plain string
  (`text/plain` on the wire, parsed as JSON regardless of the declared content type, so
  `sendBeacon` never triggers a CORS preflight). Requires an allowed `Origin`.
- `GET /stats?window=7d|30d|all`: the dashboard's one request. Memoised in isolate memory for
  60 seconds per window.
- `GET /health`: no origin restriction. Pipeline status and row counts, for eyeballing after a
  deploy.

## Privacy

No cookie is set. No IP address and no raw user agent are ever written to D1: the user agent
is classified into a device and a browser enum and discarded, and the IP is only used
in-memory to build a rate-limit key, `SHA-256(ip + IP_SALT + currentUtcDay)` truncated to 32
hex characters, which rotates daily and is never persisted. `observability` is disabled in
`wrangler.jsonc` so Cloudflare's own Workers Logs do not retain request metadata either. The
visit id is generated and held by the browser tab in a JavaScript variable, never sent to or
generated by this Worker, and never written to any storage.

## Known limits

- **`SELECT COUNT(*) FROM event WHERE env = 'prod'`**, used for the `/health` and pipeline
  row counts, is a full index scan and is the single most expensive statement this Worker
  runs. It is kept because the raw row count is a real number the dashboard shows and it must
  be true. If `rawEvents` ever exceeds roughly 500,000, replace it with a counter column on
  `rollup_state` maintained by the ingestion path, rather than counted at read time.
- **A duration reading that arrives after its day has closed and been rolled up is kept in
  the landing table but is not folded back into that day's rollup totals.** The nightly job
  re-rolls the previous day every run specifically to catch the common case (a tab restored
  from background within a day or two), but a tab resumed from bfcache after the re-roll
  window has passed leaves that one day's `daily_site`, `daily_page` and
  `daily_duration_bucket` rows permanently a little short of the raw table. The magnitude is
  small and the row itself is never lost, only left out of that day's serving-table sum.
- **No retention or deletion job exists.** At roughly 120 bytes per event row against D1's
  500 MB free ceiling, the landing table holds several million events before storage becomes
  a concern, so this has been left for when it is actually needed rather than built now.
- **Rate limiting is best effort.** `RL_COLLECT` and `RL_STATS` are optional bindings; when
  absent, every request is allowed. Origin checking is a filter, not a security boundary: a
  non-browser client can forge an `Origin` header, which is why the Worker also classifies
  every event's `env` from that header and every stats query filters to `env = 'prod'`.

## Deploying

Provisioning (`wrangler d1 create`, migrations, the `IP_SALT` secret and the first deploy) is
a one-time, hand-run sequence documented in the site's spec under Task 6. It needs a
Cloudflare account and an interactive `wrangler login`, neither of which this Worker's own
test suite or build depends on.
